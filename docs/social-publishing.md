# Social publishing — the pipeline from manifest to platforms

Written 2026-08-11, the deployment mission that took the social surface
(`docs/social-surface.md` — read that first; its §6 manifest contract is
the interface this whole document consumes) from "artifact on disk" to "a
machine that publishes it daily". Companion click-work doc:
`docs/social-apps-setup.md` — the OAuth apps only a human can create.

**The shape:** a self-hosted Postiz instance on the existing Coolify box
holds the platform connections and does the actual posting;
`scripts/social-publish.mjs` (the publisher) turns one day's manifest into
scheduled Postiz posts at staggered times; a small runner container
executes it daily at 05:00 Africa/Casablanca via a Coolify scheduled task.
Platforms not yet connected are skipped with a logged reason — the day
publishes on whatever is connected, and each platform goes live the moment
its OAuth connection lands, with no code change.

## 1. Postiz on Coolify

Service `postiz` (uuid `aaga0pmd4y7elompbck0aafl`) in project TERRA,
from Coolify's own template: `ghcr.io/gitroomhq/postiz-app:v2.10.1` +
postgres 14.5 + redis 7.2, volumes persisted (`postiz_config`,
`postiz_uploads`, `postiz_postgresql_data`, `postiz_redis_data`),
`STORAGE_PROVIDER=local`, JWT secret generated by Coolify, domain
`https://postiz.terralore.co` (TLS auto-issues once the DNS record exists —
setup doc §0). `DISABLE_REGISTRATION=true`: the admin account created at
deploy time is the only account; its credentials and the org API key live
in `/root/.postiz-admin` on the box, never in the repo.

**Resource caps** (in the service compose, `deploy.resources.limits`):
app 2.0 CPU / 1536M, postgres 1.0 CPU / 512M, redis 0.5 CPU / 256M.
Rationale: the box has 15G with roughly half in day-to-day use, and its
most memory-hungry tenant is the site's own Next build; Postiz is a
Next+Nest monolith with workers that can spike. The caps put the whole
stack's worst case near 2.3G so a runaway container hits its own cgroup
wall instead of starving a build. Postiz idles ~600–900M, so 1536M is
headroom, not a squeeze.

Upgrades: bump the image tag in the service's compose (Coolify UI or
`docker_compose_raw`) and restart — the template pin is deliberate;
`:latest` on a publishing tool is how a day silently doesn't post.

## 2. The publisher — `scripts/social-publish.mjs`

`npm run social-publish -- [--date YYYY-MM-DD] [--dry-run]` (date defaults
to *today in Africa/Casablanca*). Node stdlib only. The run:

1. Ensures the day exists — manifest on disk AND its ledger entry — else
   generates it via build-social. A manifest whose day is missing from the
   ledger is treated as foreign and rebuilt so plan and entry agree.
2. Refuses any `schemaVersion` ≠ 1, per the contract.
3. Assigns each of the five posts its slot time from
   `data/social-publish.json` and converts Casablanca wall-clock → UTC
   instant (DST-correct, two-pass offset resolution).
4. Queries Postiz (`GET /public/v1/integrations`, and the day's window of
   `GET /public/v1/posts`), decides per post: skip (with reason) or
   schedule (upload PNGs → `POST /public/v1/upload`, then
   `POST /public/v1/posts` with `type: "schedule"`).
5. Commits and pushes the day's ledger entry (see §4).
6. Writes the status line (see §6) and exits 0 only if nothing failed.

Slot defaults (committed in `data/social-publish.json`, explicitly
first-guess — revise there when real analytics exist): Pinterest anchor
07:30, Pinterest data 07:45, Instagram anchor 12:00, Instagram carousel
19:00, TikTok carousel 19:30, all Africa/Casablanca.

Platform settings ride the same config: Pinterest gets `title` (caption
first line), `link` (the manifest `targetUrl` — the pin's click-through)
and the board from `POSTIZ_PINTEREST_BOARD`; Instagram `post_type: post`;
TikTok the full required settings block with `privacy_level: SELF_ONLY`
until the audit passes (setup doc §3).

## 3. Idempotency — three layers, and why not tags

The manifest contract says: post each `dedupeKey` at most once, ever, and
keep your own posted-keys store. The publisher does that and more:

1. **Local posted-keys store** — `SOCIAL_STATUS_DIR/posted-keys.json`,
   written the moment a post is accepted. Survives container restarts (the
   status dir is a host bind mount). A key present here is never sent
   again, even if Postiz later deletes the post (deliberate un-scheduling
   in the UI stays un-scheduled).
2. **Postiz day-window query** — every post is created with a
   *deterministic id*: UUIDv5 of the dedupe key. Before scheduling, the
   publisher lists the day's posts; a matching id means "already scheduled"
   (covers a lost local store, e.g. a rebuilt runner).
3. **Server-side upsert as backstop** — Postiz upserts on the
   client-supplied post id, so even a race between two concurrent runs
   updates one row rather than double-posting.

Investigated and rejected: **Postiz tags** as the dedupe vehicle. The
public API accepts `tags: [{value,label}]` on create, but it only
*attaches tags that already exist* in the org (matched by name) — it
cannot create them, and tag creation is private-API only. A fresh dedupe
key's tag would silently drop, which is exactly the failure mode an
idempotency mechanism cannot have. The deterministic-id design needs no
pre-existing state on the Postiz side. **Customer fields** were also
ruled out: they scope *integrations* (agency mode), not posts.

Proven in dry-run (2026-08-11): first run generates and prints the 5-post
schedule; second run reprints byte-identical times in 19 ms with zero
regeneration; against live Postiz, all five report their true skip reason.

## 4. Ledger integrity

The determinism contract requires a published day's ledger entry in repo
history. After ≥1 successful schedule, the publisher commits
`data/social-ledger.json` (`Social: ledger <date> published`) and pushes
`origin main`, authenticated by a **write deploy key** (generated on the
box at `/data/terralore-social/ssh/`, registered on the GitHub repo —
key id 159960312). Push rejection → `pull --rebase` and retry (3
attempts); an unresolvable push marks the run failed (exit 1, error in the
status line) but never unschedules what Postiz already accepted — posts
going out un-recorded is recoverable (commit the ledger by hand); silently
un-posting scheduled content is not.

## 5. The runner and the schedule

Service `terralore-social-runner` (uuid `v113yzpn4rzcv32nqam70td2`,
project TERRA): a `node:22-bookworm` container that sleeps; capped 2.0
CPU / 2048M (build-social renders a day of PNGs inside it). Volumes: named
`runner_work` at `/work` (repo clone at `/work/repo`, npm cache), host
`/data/terralore-social/status` at `/status`, the deploy key read-only at
`/work/.ssh`. Both this service and postiz have
`connect_to_docker_network` enabled, so the publisher reaches Postiz as
`http://postiz-aaga0pmd4y7elompbck0aafl:5000/api` over the shared docker
network — the pipeline has **no dependency on public DNS**.

The Coolify **scheduled task** `daily-social-publish` (uuid
`kz3skwvrlasioi3td8849u7m`, on the runner service, container `runner`,
timeout 1800 s):

```
cd /work/repo && git pull --rebase origin main -q && bash scripts/social-runner-daily.sh
```

at `0 4 * * *` — Coolify schedules in UTC; 04:00 UTC is 05:00 Casablanca
in the year-round UTC+1 regime, and during the Ramadan weeks (UTC+0) the
run lands at 04:00 local: earlier, never later, and always hours before
the first 07:30 slot. The task pulls main before the script runs, so even
the script itself is current; `scripts/social-runner-daily.sh` then
re-installs deps only when the lockfile hash changed and invokes the
publisher for the current date. Task history (output + exit status) is in
Coolify under the runner service → Scheduled Tasks; a non-zero exit is how
a failed day surfaces there.

## 6. Observability — the Marsad surface

Every run appends one JSON line to
**`/data/terralore-social/status/publish-status.jsonl`** (host path on the
Hetzner box; inside the runner it's `/status/publish-status.jsonl`) and
mirrors the same object to `last-run.json` beside it:

```jsonc
{ "date": "2026-08-12", "runAt": "…", "dryRun": false, "api": "connected",
  "durationMs": 51234, "ok": true,
  "posts": [ { "dedupeKey": "2026-08-12:pinterest:anchor",
               "platform": "pinterest", "slot": "anchor",
               "action": "scheduled|skipped|failed|would-schedule",
               "reason": "…", "scheduledFor": "…Z",
               "localTime": "07:30 Africa/Casablanca" } ],
  "ledger": { "committed": true, "pushed": true } }
```

Marsad integration: scrape the file over the existing root SSH
(`ssh hetzner cat /data/terralore-social/status/last-run.json`) or bind it
into any future exporter — the path is the stable interface. `ok: false`
or a missing line for a date = the day needs eyes; `posts[].action`
carries the per-platform truth.

## 7. Runbook

- **Re-run a day** (safe, idempotent): the command in setup doc §"When
  each platform connects" — scheduled posts are skipped by key.
- **A platform disconnects** (token expiry): its posts skip with
  `platform not connected in Postiz`; reconnect the channel in Postiz and
  re-run the day.
- **Regenerating a published day is forbidden** (editorial policy,
  `docs/social-surface.md` §6) — the dedupe keys wouldn't change, so the
  publisher would refuse the duplicates anyway; delete a ledger day only
  if it was never published.
- **Coolify API access** for this stack was minted as a root-ability token
  (`social-mission-cli`, stored at `/root/.coolify-api-token` on the box).
- The publisher's own gate lives in `npm run validate`: the social
  validator now sweeps **every selectable surface × platform** through the
  caption rules (5,315 subjects — added after 2026-08-11's plan surfaced a
  Pinterest caption at 484/460 on a surface no probe day had planned; the
  ranking template now structurally drops the vintage-explainer sentence
  on Pinterest, where every row already carries its year inline).
